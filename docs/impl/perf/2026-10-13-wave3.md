# Wave 7 performance, pass 3

Baseline: `fea9d18b6c03941d73b66487ccc9ab7eee23f8eb` (the unmodified `wave7/perf3` worktree). This pass targets stationary readiness projections and their shared meal/inventory kernels. No content, schedule, horizon, decision threshold, RNG stream/key, or golden snapshot changes. No commits.

## Changes

1. Share the private projection's event/RNG callbacks and empty command list across hourly steps. Keep a fresh hourly context, so any context-local kernel memo remains scoped to its hour. The RNG callback reads the current projected minute before any hourly kernel runs.
2. Compile preparation chains once per kitchen, sharing their content-only structure within a stationary projection. Preserve recursive path order, cycle detection, first-step method selection, unit multiplication order, and per-step rounding. Every evaluation still checks current resources, quantities, preparation budget, opening, frozen state, and spoilage. Returned step arrays belong to callers. The existing projection `try/finally` releases the memo; live/travel kitchens retain it only for their own lifetime.
3. Internal inventory consumers use the existing depth-first snapshot directly, checking stack identity against the live table. Supply/weight/affordance queries and household stack collection avoid intermediate filtered depth-entry arrays. Public `stacksDeep` still returns a fresh live array. Creation, movement and container hoisting retain the existing invalidation rules; supply consumption checks live identity before drawing.

No cache enters World, save data, or the event log. Whole-readiness reuse across mutable passes was deliberately left for a dependency-key audit: pantry contents alone do not capture nutrition history, water/fire, schedules, age/date/weather, membership, pending meals or charm knowledge.

## Measurement method

All four baselines were completed before source edits, using the requested `just run run ... --no-events --profile` commands. Each optimization is followed by both generated 90-day seeds and the 30-day neighbors fixture. The final year was repeated after the green gate. Comparisons require identical final hash, byte-identical chronicle/statistics, content hash, event/retained counts, and total/per-slice save sizes.

Runs within each CLI batch are sequential. This is a shared host with parallel sibling worktrees; wall times are observations, not isolated attribution. The baseline year overlapped our separate 30-day CPU profile briefly. Generated CLI totals include generation/pre-roll outside the system timers. No phone benchmark is claimed.

CPU profiles use `node --cpu-prof`. Rankings aggregate matching function/source frames across call sites and sum `timeDeltas`; inclusive categories overlap. Separate 720-hour runs wrap each system with `process.cpuUsage()` using either a source copy extracted from the baseline commit or the working tree. A smaller interleaved before/after readiness comparison uses identical starting worlds, three seasonal dates, and asserts complete result equality and caller isolation.

## Remaining work

The phone budget is not established by these desktop runs. Roughly two-thirds of sampled work lies outside readiness, so improving this projection alone cannot close the 5 ms/hour target. Readiness still steps the shared hourly kernels exactly; the number of projections and their horizon have not changed.

Behavior-preserving candidates:

- Cache routine/observance selection and hearth-definition lookup within a stationary projection. Activity/needs own these kernels; request additive pass-scoped APIs from those owners instead of copying their rules into provisions.
- The inventory snapshot still spends time constructing location keys and looking up depth lists. A pass-local numeric holder index or exact supply-kind index may help, provided creation, definition changes on opening, deletion and container hoisting remain live and preserve traversal order.
- Memoize spoilage rate factors using exact food definition, protection classes, storage temperature and wetness band. Continue hourly accumulator/remainder stepping, rain/hem accounting, freezing and spoil-to transformations. A temperature-band-only key would lose the temperature shown in Explains.
- Audit a complete readiness input signature before reusing results across mutable passes. Include nutrition and pending meals as well as stock, placement, fire/water, schedules, age/date/weather and charms; do not key only by pantry quantity.
- Profile the production worker bundle on actual phone hardware; TSX/runtime helper costs in these CLI profiles are not a phone measurement.
- Profile same-site candidate scans on a larger regional fixture. The existing two-site run does not justify changing regional LOD or sibling social code in this pass.

Behavior-changing ideas **not implemented**: shorter/approximate readiness horizons, coarser day stepping, fewer ration/relief decisions, lower psyche cadence, smaller social candidate/memory limits, or advancing offsite households at lower fidelity. Those may improve throughput but can change choices, events or RNG outcomes and require design review.
